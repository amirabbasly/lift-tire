# راهنمای انتشار و بازگشت امن تغییرات سئوی لیفت تایر

**وضعیت:** این راهنما فقط برای اپراتور است؛ در این محیط به سرور تولید، DNS یا Search Console دسترسی نداریم و هیچ استقراری انجام نشده است. روش واقعی تولید هنوز مشخص نیست. اول روش نصب، سرویس‌ها، محل داده و نسخه فعلی را شناسایی کنید و فقط **پس از تأیید مالک و در بازه توافق‌شده** ادامه دهید. هیچ‌یک از دستورهای زیر نباید بدون تطبیق با محیط واقعی اجرا شود. اگر هر بررسی ناموفق بود، متوقف شوید؛ پیش‌نمایش محلی یا push به GitHub به معنی انتشار زنده نیست.

## هشدار مهم درباره اسکریپت‌های قدیمی

`deploy.sh update` در شکست backup، fetch، checkout یا pull ممکن است ادامه دهد؛ `deploy.sh backup` نیز در بعضی خطاها شکست بکاپ آپلودها را صرفاً هشدار می‌دهد. `scripts/deploy-pm2.sh` در مسیر restart دارای fallback به `pm2 restart all` است و مسیرهای install/up ممکن است seed، تغییر تنظیمات یا دست‌کاری سرویس داشته باشند. برای این انتشار از آن‌ها استفاده نکنید. `seed --force`، `destroy`، `clean`، `git reset --hard`، تغییر `.env`، بازنویسی nginx، `pm2 delete all` و `pm2 kill` جزو این انتشار نیستند. هر بازیابی داده یا تغییر سرویس دیگر نیازمند تأیید جداگانه است.

## ۱. شناسایی فقط‌خواندنی پیش از تأیید

- مسیر واقعی پروژه و کاربر سرویس را از مدیر سرور بگیرید. `git status --short`، `git branch --show-current` و `git rev-parse HEAD` را در checkout واقعی بررسی و نسخه جاری را ثبت کنید؛ اگر فایل تغییریافته یا بدون پیگیری وجود دارد، قبل از بررسی آن‌ها هیچ pull/merge انجام ندهید. تغییر محلی ارزشمند را بازنویسی نکنید.
- برای تشخیص Compose، در مسیر نصب `docker compose ps` و `docker compose images` را ببینید؛ برای PM2، با کاربر مالک فرایند `pm2 list` و `pm2 describe lifttire-web` را بررسی کنید. وجود فایل Compose یا ecosystem در مخزن، به‌تنهایی اثبات روش تولید نیست. اگر هر دو یا هیچ‌کدام فعال‌اند، اجرای دستور را متوقف و معماری واقعی را مشخص کنید.
- بررسی کنید API و پایگاه واقعاً PostgreSQL هستند یا PGlite، volume/مسیر upload کجاست، nginx به کدام upstream وصل است و نسخه پشتیبان قابل بازگشت کجاست. `docker inspect`/لاگ‌ها ممکن است رازها یا اطلاعات کاربران را نشان دهند؛ خروجی محیط و `.env` را در چت یا مخزن منتشر نکنید.
- تفاوت commit نصب‌شده و commit تأییدشده را با `git diff --stat` و `git diff --name-only` بررسی کنید. در این دور تغییری در schema دیتابیس یا کد backend مورد نیاز نبوده است؛ اگر اختلاف واقعی نسخه تولید تا نسخه انتشار شامل backend، Compose، وابستگی یا مهاجرت دیگری است، آن را جداگانه بررسی کنید و فرض نکنید تغییر فقط frontend است.
- صاحب فروشگاه باید قیمت، موجودی، مشخصات، نظرات، راه‌های تماس و ادعاهای موجود در داده و صفحه اصلی را تأیید کند. در این مخزن داده seed نمونه است، API دریافت جزئیات سفارش با کد بدون احراز هویت دیده شده و درگاه پرداخت mock است؛ تا رفع و تأیید جداگانه برای فروش واقعی اعلام آمادگی نکنید.

## ۲. بعد از تأیید: بکاپ قابل بررسی و نسخه قبلی

پیش از هر تغییر، از commit فعلی، نام/ID image وب یا مسیر release قبلی، تنظیمات مؤثر بدون انتشار رازها و روش بازگشت یادداشت بردارید. بکاپ دیتابیس، آپلودها و پیکربندی محرمانه را به محل امن با دسترسی محدود ببرید و ترجیحاً قابلیت بازخوانی را در محیط **جداگانه** بررسی کنید. بازگردانی دیتابیس روی محیط زنده می‌تواند سفارش‌های جدید را حذف کند و بخشی از rollback عادی فرانت‌اند نیست.

برای نمونه، **فقط اگر** همین Compose مخزن و سرویس `postgres` و کانتینر `lifttire_api` با مسیر آپلود `/app/uploads` واقعاً در حال استفاده‌اند، اپراتور پس از تأیید می‌تواند در پوشه نصب این نمونه را با shell مناسب اجرا کند:

```bash
set -euo pipefail
umask 077
BACKUP_DIR="$(pwd)/backups/pre-seo-$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -p "$BACKUP_DIR/uploads"
docker compose exec -T postgres sh -c 'exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' > "$BACKUP_DIR/database.dump"
test -s "$BACKUP_DIR/database.dump"
docker compose exec -T postgres pg_restore -l < "$BACKUP_DIR/database.dump" > /dev/null
docker cp lifttire_api:/app/uploads/. "$BACKUP_DIR/uploads/"
# اندازه و چند تصویر شناخته‌شده را بازبینی کنید؛ سپس نسخه امن خارج از سرور بگیرید.
du -sh "$BACKUP_DIR/database.dump" "$BACKUP_DIR/uploads"
```

این آزمون فقط ساختار dump و کپی را بررسی می‌کند، نه صحت کامل بازیابی؛ تست restore جداگانه لازم است. نام واقعی کانتینر، مسیر upload و حجم داده را اول تأیید کنید. برای PostgreSQL بیرون از Compose یا PGlite، روش بکاپ سازگار و سازگار با نوشتن هم‌زمان را از مسئول پایگاه بگیرید؛ کپی خام PGlite باز را بکاپ سازگار فرض نکنید. در نبود بکاپ معتبر یا برنامه بازگشت، ادامه ندهید.

## ۳. رساندن کد تأییدشده، بدون تغییر شاخه سرور

نسخه انتشار باید قبلاً روی منبع تأییدشده تیم موجود و hash کامل آن مشخص باشد. در checkout واقعی، شاخه فعلی را عوض نکنید، تغییرات محلی را کنار نزنید و از pull مبهم استفاده نکنید. پس از بررسی clean بودن checkout و پس از تنظیم متغیرها با مقادیر واقعی تأییدشده، نمونه زیر فقط fast-forward مجاز را می‌پذیرد:

```bash
set -euo pipefail
: "${RELEASE_BRANCH:?نام شاخه تاییدشده منبع را تنظیم کنید}"
: "${EXPECTED_COMMIT:?شناسه کامل commit تاییدشده را تنظیم کنید}"
test -z "$(git status --porcelain)" || { echo 'تغییر محلی وجود دارد؛ توقف.' >&2; exit 1; }
git fetch origin "$RELEASE_BRANCH"
test "$(git rev-parse FETCH_HEAD)" = "$EXPECTED_COMMIT" || { echo 'commit دریافتی با نسخه تاییدشده فرق دارد؛ توقف.' >&2; exit 1; }
git merge-base --is-ancestor HEAD FETCH_HEAD || { echo 'به fast-forward قابل اعمال نیست؛ توقف.' >&2; exit 1; }
git merge --ff-only FETCH_HEAD
test "$(git rev-parse HEAD)" = "$EXPECTED_COMMIT"
```

اگر وضعیت تولید، شاخه انتشار یا سیاست تیم اجازه این روش را نمی‌دهد، مسیر انتشار تیم را بعد از تأیید طی کنید و برای حل تعارض دست به reset/checkout اجباری نزنید. دو مقاله تازه هنوز تاریخ انتشار عمومی ندارند: `sort_at` فقط ترتیب محلی است. بعد از تعیین تاریخ واقعی انتشار، در صورت تمایل `created_at` و `updated_at` همان دو مقاله در `frontend/lib/seo-editorial-posts.js` با تاریخ واقعی ثبت، بازبینی و در انتشار مناسب build شوند؛ تا آن زمان ادعای تاریخ انتشار در صفحه/schema وجود ندارد.

## ۴. اگر و فقط اگر تولید از Docker Compose همین پروژه استفاده می‌کند

پیش‌شرط: بکاپ بررسی‌شده، نسخه دقیق، تنظیمات موجود و خروجی build تأیید شده باشند. فقط وب در این دور نیازمند بازسازی است؛ به API، postgres، volumeها، nginx، احراز هویت و درگاه دست نزنید. ابتدا image فعلی وب را با ID ذخیره کنید؛ نام واقعی سرویس/پروژه را با `docker compose ps` تطبیق دهید:

```bash
set -euo pipefail
WEB_CONTAINER="$(docker compose ps -q web)"
test -n "$WEB_CONTAINER"
OLD_WEB_IMAGE_ID="$(docker inspect --format '{{.Image}}' "$WEB_CONTAINER")"
printf 'Previous web image ID: %s\n' "$OLD_WEB_IMAGE_ID"
# مقدار را در دفتر انتشار امن نگه دارید و مطمئن شوید image پاک نمی‌شود.
docker compose build web
docker compose up -d --no-deps web
docker compose ps web
docker compose logs --tail=100 web
```

`NEXT_PUBLIC_SITE_URL` و در صورت استفاده `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION` موقع build در image وارد می‌شوند؛ مقدار فعلی و دامنه را **بدون افشای راز** کنترل کنید. تغییر آن‌ها با صرف restart اعمال نمی‌شود. اگر build خطا داد، سرویس را بازآفرینی نکنید. بعد از تعویض کانتینر، HTTP و upstream را بررسی کنید؛ اگر nginx آدرس قدیمی را نگه داشت و ۵۰۲ داد، تنها پس از تأیید مسئول، پیکربندی nginx همان پروژه را بررسی و در صورت نیاز فقط همان nginx را reload کنید؛ سرویس نامرتبط را restart نکنید.

**بازگشت وب:** روش سازمان و image ID قبلی را به‌کار ببرید. اگر با `docker compose images web` تأیید شده که برچسب وب دقیقاً `lifttire-web:latest` است و هیچ سرویس دیگری از آن استفاده نمی‌کند، پس از تأیید اپراتور می‌توان image ثبت‌شده را مجدداً به همان نام tag و فقط وب را با `docker compose up -d --no-deps --no-build web` بازآفرینی کرد. اگر نام image، تنظیمات یا سازگاری نسخه قبلی معلوم نیست این روش را اجرا نکنید. پس از rollback، بررسی کنید checkout هنوز commit جدید را نشان می‌دهد و build بعدی ناخواسته نسخه برگشتی را جایگزین نکند؛ ثبت و اصلاح وضعیت کد با روش انتشار تیم انجام شود. دیتابیس را به‌طور خودکار restore نکنید.

## ۵. اگر و فقط اگر تولید از PM2 استفاده می‌کند

با همان کاربر مالک PM2 نام، مسیر اجرایی/cwd و محیط `lifttire-web` را بررسی کنید. یک release جداگانه با همان commit و تنظیمات build واقعی آماده کنید: در `frontend`، `npm ci --no-audit --no-fund` و سپس `npm run build`؛ `API_INTERNAL_URL` باید به API داخلی واقعی اشاره کند و URL عمومی و verification در زمان build درست باشند. برای standalone، محتویات `frontend/public` و `frontend/.next/static` باید در `frontend/.next/standalone/public` و `frontend/.next/standalone/.next/static` قرار گیرند. روی checkout زنده و فایل‌های release جاری overwrite نکنید.

اگر زیرساخت موجود، release جداگانه و انتخاب اتمیک مسیر را پشتیبانی می‌کند، اپراتور پس از تأیید آن مسیر را با سازوکار موجود به نسخه جدید تغییر دهد و **فقط** `lifttire-web` را با تنظیمات درست reload کند؛ سپس `pm2 describe lifttire-web` و `pm2 logs lifttire-web --nostream --lines 100` را بررسی کند. مثلاً `pm2 reload lifttire-web --update-env` تنها زمانی مناسب است که مطمئن باشید PM2 واقعاً از مسیر release انتخاب‌شده و محیط درست استفاده می‌کند؛ reload به‌تنهایی تضمین تغییر cwd نیست. اگر این سازوکار ناشناخته است، متوقف شوید و مسئول سرور آن را تعیین کند. برای rollback، مسیر release تأییدشده قبلی و محیط سازگار را با همان سازوکار بازگردانید و فقط وب را reload و آزمایش کنید. API یا فرایندهای دیگر را restart نکنید.

## ۶. بررسی پس از انتشار و لاگ

۱. نسخه اجراشده، سلامت وب و API و خطاهای همان سرویس را با روش نصب واقعی بررسی کنید. در Compose می‌توان `docker compose logs --tail=100 web` و در PM2 لاگ اختصاصی فوق را خواند؛ اطلاعات مشتری/توکن را منتشر نکنید.
۲. از بیرون سرور با درخواست GET، کد واقعی HTTP، گواهی HTTPS، canonical و محتوای `/`، `/products`، یک محصول **واقعی تأییدشده**، `/category/passenger`، `/brands/barz`، `/brands/kavir`، `/blog` و دو مقاله تازه را بررسی کنید. صفحه ۴۰۴ نباید به‌عنوان موفقیت محسوب شود. برای نمونه `curl -sS -o /dev/null -w '%{http_code}\n' https://lift-tire.com/blog`؛ انتخاب دامنه و محصول واقعی بر عهده اپراتور است.
۳. `/robots.txt` و `/sitemap.xml` را بخوانید؛ URLهای تازه باید با دامنه canonical صحیح، بدون مسیر خصوصی یا کالای غیرواقعی ظاهر شوند. در HTML محصول، صحت قیمت/واحد، موجودی و Product schema را با داده همان محصول کنترل کنید. رپورتاژ، نشان و لینک `sponsored` را در HTML زنده جداگانه کنترل کنید.
۴. در موبایل و دسکتاپ، صفحه اصلی و ناوبری، فهرست، مقاله، سبد و ورود را بررسی کنید. تراکنش واقعی، ساخت سفارش یا پرداخت را بدون هماهنگی و داده آزمایشی مناسب اجرا نکنید. لاگ و خطا، زمان شروع/پایان، نسخه و نتیجه را در دفتر انتشار ثبت کنید.
۵. در صورت خطای جدی، تغییرات را متوقف و با فرآیند بازگشت تأییدشده فقط وب را به نسخه قبلی برگردانید؛ دوباره همان بررسی‌ها را انجام دهید. موفقیت build به‌تنهایی موفقیت انتشار نیست.

پس از تأیید سلامت نسخه زنده، مالک شخصاً [راهنمای Search Console](seo-search-console.md) و [گزارش URLها](seo-url-report.md) را دنبال کند؛ ثبت نقشه یا درخواست خزش تضمین ایندکس نیست.
